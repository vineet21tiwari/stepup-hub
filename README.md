# StepUp Hub — Phase 1

"Step Up in Studies, Step Ahead with Confidence"

Phase 1 delivers the full booking loop across four roles — **Student, Teacher, Coordinator, Admin** — on three
codebases that share one backend:

- **backend/** — Java Spring Boot REST + WebSocket API, H2 file database (zero setup, no external DB needed)
- **web/** — React (Vite) web app for all four roles
- **mobile/** — Flutter app (Android/iOS) for all four roles

## What's included in Phase 1

- Signup/login for Student, Teacher, Coordinator, Admin (JWT auth)
- Admin creates courses
- Teachers apply to teach a course → Admin approves (this also activates the teacher's profile)
- Students browse courses → see approved teachers → see each teacher's open slots → book a slot
- Two-step approval: **Teacher approves → Admin approves** → class is scheduled automatically
- All participants (student, teacher, coordinator once assigned, admin) can see the scheduled class
- Common chat room per class session (real-time via WebSocket on web, polling on mobile)
- In-app notifications for every step (application submitted/approved, booking requested/approved/rejected,
  class scheduled) — a background job also fires a reminder shortly before each class starts
- Admin assigns a Coordinator to a scheduled class

## 1. Backend (Spring Boot)

**Requirements:** Java 17+, Maven (or use the included `mvnw` if you add one — a system Maven install works fine).

```bash
cd backend
mvn spring-boot:run
```

The API starts on **http://localhost:8080**. It uses a file-based H2 database (`backend/data/stepuphub.mv.db`),
so your data persists across restarts. Delete that `data/` folder to reset everything.

On first run it seeds one admin account:
- **admin@stepuphub.com / Admin@123**

Useful local endpoints:
- `http://localhost:8080/h2-console` — H2 web console (JDBC URL: `jdbc:h2:file:./data/stepuphub`, user `sa`, no password)
- WebSocket endpoint: `ws://localhost:8080/ws` (STOMP, topics `/topic/session/{sessionId}` and `/topic/user/{userId}`)

> Note: this was scaffolded in a sandboxed environment without access to Maven Central, so it hasn't been
> build-tested end-to-end here. On your machine (with normal internet access) `mvn spring-boot:run` will pull
> all dependencies from Maven Central automatically. If anything doesn't compile, check the Java version first
> (`java -version` should show 17+).

## 2. Web app (React + Vite)

**Requirements:** Node.js 18+

```bash
cd web
npm install    # only needed if node_modules isn't already present
npm run dev
```

Opens on **http://localhost:5173**. It talks to the backend at `http://localhost:8080` by default — override with
a `.env` file containing `VITE_API_BASE_URL=http://your-backend:8080` if needed.

This was build-tested in this environment (`npm run build` succeeds).

## 3. Mobile app (Flutter)

**Requirements:** Flutter SDK (stable channel), Android Studio / Xcode for a device or emulator.

The `mobile/` folder currently has the Dart source (`lib/`) and `pubspec.yaml` but not the generated native
Android/iOS project folders (those can only be generated by the Flutter SDK itself, which isn't available in the
sandbox this was built in). Generate them once on your machine:

```bash
cd mobile
flutter create .          # adds android/ ios/ (and web/, etc.) around the existing lib/ and pubspec.yaml — safe, won't overwrite them
flutter pub get
flutter run
```

**Backend URL:** by default the app points at `http://10.0.2.2:8080`, which is the correct address for the
**Android emulator** to reach your machine's localhost. Override it for other targets:

```bash
# iOS simulator or a physical device on the same Wi-Fi as your backend
flutter run --dart-define=API_BASE_URL=http://YOUR_MACHINE_LAN_IP:8080
```

Mobile covers the same four roles as web (login/signup, course browsing & booking for students, slot & approval
management for teachers, class oversight for coordinators/admins, in-app notifications, and the common class chat)
with a simplified single-column layout suited to a phone. Chat and notifications refresh by polling every few
seconds rather than a persistent WebSocket, to keep the mobile client simple for Phase 1.

> This code hasn't been compiled here either (no Flutter SDK in this sandbox) — I did a careful manual review
> (balanced braces/parens, verified every import path, cross-checked every API call against the actual backend
> controllers) but please run `flutter analyze` after `flutter pub get` on your machine and let me know if
> anything needs fixing — I can iterate quickly from an error message.
